Backend Spring Boot construido con Arquitectura Hexagonal

Visión General de la Arquitectura

El backend de iMirly es una aplicación Spring Boot 4.0.3 construida utilizando Arquitectura Hexagonal (patrón Ports and Adapters). Esta arquitectura asegura una separación limpia entre la lógica de negocio y las preocupaciones de infraestructura.

Stack Tecnológico

Framework
Spring Boot 4.0.3
Lenguaje
Java 25
Base de Datos
PostgreSQL
Seguridad
Spring Security + JWT

Estructura del Proyecto

La aplicación sigue una estructura de monolito modular con contextos delimitados distintos:

src/main/java/tfg/imirly/
├── IMirlyApplication.java # Punto de entrada Spring Boot
├── auth/ # Módulo de autenticación
│ ├── domain/ # Lógica de negocio
│ │ ├── model/
│ │ └── port/out/
│ ├── application/ # Casos de uso
│ │ ├── port/in/
│ │ └── service/
│ └── infrastructure/ # Adaptadores externos
│ ├── input/rest/
│ └── output/
│ ├── persistence/
│ └── security/
└── catalog/ # Módulo de catálogo
├── domain/
├── application/
└── infrastructure/

Módulos Principales

Módulo Auth

Maneja autenticación de usuarios, registro y gestión de perfiles:

  • Registro y login de usuarios
  • Generación y validación de tokens JWT
  • Encriptación de contraseñas con BCrypt
  • Gestión de perfiles de usuario
  • Funcionalidad de monedero virtual

Módulo Catalog

Gestiona los listados de servicios:

  • Anuncios de servicios (AnuncioServicio)
  • Categorías y subcategorías
  • Gestión de favoritos
  • Búsqueda y filtrado de servicios

Configuración

Properties
application.properties 
spring.application.name=iMirly
spring.datasource.url=jdbc:postgresql://localhost:5432/imirly_db
spring.datasource.username=user_imirly
spring.datasource.password=password_imirly
spring.jpa.hibernate.ddl-auto=update
spring.jpa.show-sql=true

La configuración spring.jpa.hibernate.ddl-auto=update actualiza automáticamente el esquema de la base de datos basándose en las definiciones de entidades durante el desarrollo.

¿Por qué Arquitectura Hexagonal?

Testabilidad

La lógica de negocio puede probarse sin dependencias de infraestructura

Flexibilidad

Fácil cambiar implementaciones (ej: de PostgreSQL a MongoDB)

Mantenibilidad

La clara separación de responsabilidades hace el código más fácil de entender y modificar

Independencia Tecnológica

La lógica de dominio no depende de frameworks o librerías externas
